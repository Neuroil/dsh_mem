# dsh-mem 性能基准测试与分析（benchmark/）

> 对本插件（dsh-mem v0.2.0）的存储、检索、写入、睡眠巩固四条链路做规模化的性能测试与空间利用率分析。
> 全部脚本对 `../lib`（`npm run build` 的生产构建产物）计时——被测代码即生产代码，benchmark 只注入介质与模型替身。
> 实测环境：Node v24.14.1 · win32 x64 · AMD Ryzen 7 9700X（8C/16T）· 1024 维 deterministic 嵌入 · 2026-10-25。

## 怎么跑

```bash
# 仓库根目录（benchmark 直接 import lib/，宿主 loader 不转译 TS）
npm run build

cd benchmark
npm install          # 仅装 sqlite 后端（@deepseek-ai/dsh-storage-sqlite，与宿主逐位同版）
npm run all          # 顺序跑全部五项（互不抢 CPU），约 3–4 分钟
# 或单项：
npm run insert       # A 批量插入（memory + sqlite 双介质）
npm run retrieval    # B 大量检索（similar + 四级管线 + 阶段归因）
npm run write        # C 写入管线每轮成本（随库规模/候选数/矛盾分支/介质）
npm run sleep        # D 睡眠巩固周期（聚类 O(N²) + 完整周期）
npm run space        # E 空间利用率与内存占用
```

原始数字（含每 op 采样汇总）落在 `results/*.json`（gitignore，随跑随生成）；`node smoke.mjs` 是基建自检。各脚本均支持 `--scales` 覆盖规模，如 `node bench-insert.mjs --scales 1000,2000 --sqlite-scales 500`。

## 方法论

- **介质两档**：`memory`（内存 KvUnit，剥离持久化 → 插件纯计算）与 `sqlite`（生产推荐后端 `dsh-storage-sqlite`，WAL，每条 `putRecord` 一次 autocommit → 真实持久化吞吐）。检索/聚类的热路径全在内存镜像上，介质只影响 `MemoryStore.open`（重开，即宿主重启路径）。
- **模型替身**：嵌入用插件自带 `deterministic` 模式（词袋哈希，1024 维、与生产 bge-m3 同维数，成本结构相同）；LLM 判定用按 system 提示词分流的合法 JSON 替身（零网络延迟）。**因此本套数字是插件侧开销的下界**——生产中每轮写入另有 1+c 次 LLM 调用、每次检索另有 1 次嵌入 HTTP 调用（秒级/百毫秒级，见「生产语境校准」）。
- **语料**：种子 PRNG 驱动的确定性合成语料（12 主题族、中英双语、真实记忆长度），族内 token 重叠使近邻/CSLS 阶段在非退化分布上计时；睡眠周期用专用「成簇语料」（组内基句 + 近重复变体，模拟同一事件的多次记录——压缩的真实输入形态）。同种子跨机可复现。
- **计时与拟合**：逐 op `performance.now()` 采样（mean/p50/p95）+ 批量吞吐；规模曲线做幂律拟合 `t = a·N^b`，b 即经验复杂度指数（0≈O(1)，1≈O(N)，2≈O(N²)）。
- **已知口径差**：`clusterCos=0.75` 是给真实嵌入的阈值；deterministic 嵌入余弦分布不同，睡眠基准先采样组内/组间分布自动校准阈值（本次 0.69），保证聚类路径被真实执行。`contradictionMinCos` 在 contradicts 变体中降为 0.1（同 e2e-write 的处理），原因相同。

## A · 批量插入

写入路径对每条记忆做两次介质写：`putRecord`（落库）+ `refreshNeighborhood`（邻域统计回写，内含一次 O(N) 全库近邻扫描）。

**memory 介质（纯计算：索引维护 + O(N) 近邻扫描）**

| N | put mean(ms) | put p95(ms) | put ops/s | refresh mean(ms) | refresh p95(ms) | refresh ops/s | 重开(ms) |
|---|---|---|---|---|---|---|---|
| 1,000 | 0.025 | 0.04 | 40,197 | 4.116 | 4.75 | 243 | 27.0 |
| 2,000 | 0.030 | 0.04 | 32,789 | 8.257 | 8.89 | 121 | 65.2 |
| 5,000 | 0.028 | 0.03 | 35,485 | 21.605 | 24.17 | 46 | 163.4 |
| 10,000 | 0.030 | 0.04 | 32,956 | 45.008 | 49.26 | 22 | 315.6 |
| 20,000 | 0.029 | 0.03 | 34,602 | 94.898 | 110.81 | 11 | 818.5 |

**sqlite 介质（生产后端：WAL，逐条 autocommit）**

| N | put mean(ms) | put ops/s | refresh mean(ms) | refresh ops/s | 重开(ms) |
|---|---|---|---|---|---|
| 500 | 0.332 | 3,008 | 2.478 | 404 | 16.1 |
| 1,000 | 0.319 | 3,132 | 5.120 | 195 | 33.2 |
| 2,000 | 0.335 | 2,985 | 10.238 | 98 | 63.3 |
| 5,000 | 0.333 | 3,003 | 24.874 | 40 | 183.9 |
| 10,000 | 0.320 | 3,126 | 46.702 | 21 | 338.4 |

**经验复杂度指数 b**（t = a·N^b）：put **memory 0.04 / sqlite −0.00**（O(1)，吞吐与规模无关）；refresh **memory 1.05 / sqlite 0.98**（O(N)）；重开 **memory 1.10 / sqlite 1.03**（O(N)，≈34 µs/记录，sqlite 含 loadAll JSON 解析 + 索引重建）。

**读数**：单条落库很便宜（内存 3.4 万条/s、sqlite 3 千条/s——后者的每条 0.32ms 几乎全是 WAL autocommit 的固定成本，与库大小无关）；**贵的是 refreshNeighborhood**，它随库线性增长并在 N≈150 时就超过 put 本身（4.1ms vs 0.33ms @1k）。宿主重启的重开成本线性、无惊喜（1 万条 0.34s）。

## B · 大量检索

检索全部发生在内存镜像 + 内存索引上（介质不影响热路径，见 A 的重开列），故用 memory 介质。100 条全族查询/规模。

| N | similar(k=5) mean(ms) | similar p95(ms) | 全管线 mean(ms) | 全管线 p95(ms) | QPS |
|---|---|---|---|---|---|
| 1,000 | 3.785 | 3.84 | 4.284 | 4.79 | 233 |
| 2,000 | 8.236 | 8.74 | 8.504 | 9.31 | 118 |
| 5,000 | 21.578 | 23.25 | 20.744 | 21.72 | 48 |
| 10,000 | 43.089 | 45.50 | 43.689 | 49.84 | 23 |
| 20,000 | 94.284 | 108.26 | 92.889 | 109.35 | 11 |

经验指数 b：similar **1.06**（R²=1.000）、全管线 **1.02**（R²=0.999）——纯线性。

**阶段归因 @N=20,000**（单次 ms）：

| 阶段 | ms | 说明 |
|---|---|---|
| `retrievable()` 物化 | 0.660 | 产出 20,000 条 L0 候选 |
| 查询嵌入（deterministic） | 0.004 | 生产为一次 HTTP 调用（数十至数百 ms，不在本基准） |
| **L0 余弦全扫 + 排序（复刻）** | **95.265** | 20,000 × 1024 维余弦 + sort |
| 精排 rerank（deterministic） | 0.133 | 20 文档；生产为 HTTP |

**读数**：四级管线里 CSLS / 精排 / MMR 合计不到 1ms——**L0 的暴力余弦全扫 + 排序就是全部成本**（向量索引是精确 kNN 的 P0 实现，设计上就为替换 ANN 留了接口）。写入路径的矛盾判定近邻扫描（`similar`）与之同源、同为 O(N)。

## C · 写入管线每轮成本

真实 `WritePipeline.processTurn`（deterministic 嵌入 + LLM 替身），20 轮/变体。生产每轮另有 1+c 次 LLM 调用的网络与推理时间（c=4 时约 9 次调用）。

| 变体 | 库规模 N | 候选 c | 每轮 mean(ms) | p95(ms) | 每候选(ms) |
|---|---|---|---|---|---|
| baseline | 0 | 4 | 2.1 | 4.2 | 0.52 |
| baseline | 1,000 | 4 | 40.2 | 42.0 | 10.06 |
| baseline | 5,000 | 4 | 198.6 | 207.4 | 49.65 |
| baseline | 10,000 | 4 | 419.5 | 486.9 | 104.87 |
| c=8 | 10,000 | 8 | 820.0 | 854.5 | 102.50 |
| contradicts | 5,000 | 4 | 203.2 | 227.0 | 50.79 |
| sqlite 介质 | 1,000 | 4 | 44.4 | 48.3 | 11.11 |

每轮成本随库规模的经验指数 **b = 1.01**（仅 N≥1 点）——线性，由每候选的 `similar`（矛盾判定近邻）与 `refreshNeighborhood` 两次 O(N) 扫描主导；随候选数 c 也线性（c=8@10k ≈ 2×c=4）。矛盾命中（软失效路径）只增加 ~2%（多两次介质写）；sqlite 持久化份额 @1k 约 +10%。

**读数**：插件侧每轮开销在 1 万条库上约 0.4s（c=4），与一次真实 LLM 调用同量级但小于 9 次调用之和；库到 4–5 万条时插件侧开销将反超 LLM 网络/推理时间，成为写入时延主体。

## D · 睡眠巩固周期

`buildClusters` 是全量 pairwise 余弦连边（O(N²·d)）+ 簇内均值闸门；完整周期还要做 gist/QA/路由（LLM 替身全放行）与**第 7 步全库刷新**（每条幸存记录 `updateRecord` + `refreshNeighborhood` = 2 次介质写 + 1 次 O(N) 扫描）。

**buildClusters 规模曲线**（成簇语料，clusterCos=0.69 校准值）：

| N | 耗时(ms) | pair/s | 簇数 | 覆盖记录 | 均值簇大小 |
|---|---|---|---|---|---|
| 250 | 123.1 | 252,897 | 10 | 199 | 19.9 |
| 500 | 493.0 | 253,043 | 10 | 407 | 40.7 |
| 1,000 | 2,105.5 | 237,238 | 9 | 741 | 82.3 |
| 2,000 | 9,362.3 | 213,517 | 8 | 1,324 | 165.5 |

**SleepCycle.run 完整一轮（N=1,000，9 簇：1 new_node + 8 attached，741 条压缩迁移，幸存 259 条）**：

| 介质 | 总耗时(ms) | 其中聚类(ms) | 介质写 |
|---|---|---|---|
| memory | 3,041.6 | 2,016.4 | 1,270 |
| sqlite | 3,725.6 | 2,091.1 | （同口径 1,270 次） |

**读数**：聚类吞吐稳定在 ~21–25 万对/s（b≈2，4 倍规模 4 倍多耗时）。**外推是本插件第一堵规模墙**：1 万条约 4 分钟、2 万条约 15–16 分钟——且这是每攒 `minNewMemories`(10) 条就可能在后台触发一次的成本（turn/end 门控）。若一轮无簇可压缩（通用语料的常态），第 7 步仍会全库刷新：N 条 × O(N) 扫描 + 2N 次介质写，与聚类同为 O(N²) 量级（1 万条无压缩库 ≈ 8 分钟纯刷新）。

## E · 空间利用率与内存占用

**磁盘：逻辑负载 vs sqlite 物理**（逻辑 = 紧凑 JSON，即 value 列内容口径；文件 = close 后库文件）：

| N | 逻辑紧凑 JSON | sqlite 文件 | payload 列 | 文件/payload | 每记录（文件 B） | 每记录（逻辑 B） | embedding 占比 |
|---|---|---|---|---|---|---|---|
| 1,000 | 3,107KB | 4,104KB | 3,134KB | 1.31× | 4,202 | 3,182 | 83.5% |
| 5,000 | 15,649KB | 20,380KB | 15,803KB | 1.29× | 4,174 | 3,205 | 83.5% |
| 10,000 | 31,343KB | 40,732KB | 31,664KB | 1.29× | 4,171 | 3,210 | 83.5% |

**构成与假设（N=10,000）**：

| 口径 | 体积 | 相对当前 |
|---|---|---|
| 紧凑 JSON（当前 sqlite value 口径） | 31,343KB | 1.00× |
| int8 + base64 量化嵌入（假设） | 18,521KB | **0.59×（−41%）** |
| json 后端模拟（2 空格 pretty 近似） | 103,277KB | 3.30× |

**增长行为（N=10,000，同一库文件连续阶段）**：

| 阶段 | 写入量 | 耗时(ms) | 库文件 | freelist 页 |
|---|---|---|---|---|
| 初始插入 | 10,000 条 | — | 40,732KB | — |
| 全量改写（r_m 刷新 1,000 条） | 1,000 条 | 40,676 | 40,732KB（原地覆写，零增长） | 0 |
| 10% 取代 churn | 1,000 新 + 1,000 失效 | 633 | 44,804KB（+4KB/新记录） | 0 |
| clearAll（硬删 11,000 条） | 11,000 条 | 3,160 | 44,804KB（页进 freelist，文件不变） | — |
| VACUUM 后 | — | — | **36KB** | — |

**内存镜像堆占用**：每记录 ≈ 14–17KB（记录对象 + 索引内归一化向量副本，不含嵌入原始数组；两次独立测量 13.9KB/17.0KB，含 GC 噪声）。1 万条 ≈ 150MB 常驻堆。

**读数**：sqlite 对紧凑 JSON 的物理开销稳定在 **1.29×**（页开销 + key 列 + b-tree），没有任何惊喜；**83.5% 的逻辑负载是嵌入本身**——1024 维 float 以十进制文本存进 JSON（每条 ≈ 2.7KB），这是空间问题的主矛盾，也是 TODO 中 int8+base64 量化项的量化依据（**−41%**，同时把 loadAll 的 JSON 解析量与堆占用砍半）。记录永不删除（§2.5）在空间上的代价是**软失效记录全量滞留**（churn 每次取代净 +4KB/条），clearAll 后空间只有 VACUUM 才真正归还（后端不暴露 VACUUM，运维需手工压实）。json 后端 pretty-print 模拟值 3.3× 与 README 早期实测（341KB 中 78% 缩进空白）一致——当初切 sqlite 的决定被定量复认。

## 综合分析

### 成本地图（全部实测锚定）

| 操作 | 复杂度 | 斜率量级 | 首要成因 |
|---|---|---|---|
| putRecord（sqlite） | O(1) | 0.32ms/条 | WAL autocommit 固定成本 |
| putRecord（memory） | O(1) | 0.03ms/条 | 索引维护 + 镜像 |
| similar / L0 检索 / refreshNeighborhood | O(N) | ≈4.5µs/条·1024 维 | 暴力余弦全扫 + sort |
| 每轮写入（c 候选） | O(N·c) | c=4 时 ≈40µs/条·库 | 每候选两次 O(N) 扫描 |
| 重开（宿主重启） | O(N) | ≈34µs/条 | loadAll JSON 解析 + 索引重建 |
| buildClusters（睡眠） | **O(N²)** | ≈21–25 万对/s | 全量 pairwise 余弦 |
| 睡眠第 7 步全库刷新 | **O(N²)** 最坏 | N×(2 写+O(N) 扫) | 无增量性：全库每轮重算 r_m |

### 四堵规模墙（按到顶先后排序）

1. **睡眠聚类 O(N²)**：2 千条 9.4s → 1 万条约 4 分钟 → 2 万条约 16 分钟，且周期触发门槛仅为 10 条新写入。**第一堵墙**。
2. **堆占用 ≈14–17KB/条**：10 万条 ≈ 1.5GB 常驻堆。第二堵墙（长驻宿主进程）。
3. **磁盘 ≈4.2KB/条**（83.5% 是嵌入）：10 万条 ≈ 420MB/工作区。比堆墙靠后（磁盘比堆便宜）。
4. **L0 线性扫描**：单查询 20k 条 93ms、QPS 11——交互式检索尚可接受，10 万条约 0.5s/查询。最后一堵墙（但写入路径每轮的两次 O(N) 扫描让它提前到顶：10 万条库每轮写入仅插件侧就要 ~4s）。

### 生产语境校准（本套数字如何映射到真实部署）

- **检索时延** = 本套全管线数字 + 一次嵌入 HTTP（真实 bge-m3，经验 50–200ms）。当前规模（≤2 万条）**网络是检索时延的大头**，L0 尚在其次；两者在 ~5 万条交叉，之后 L0 主导。
- **写入时延** = 本套每轮数字 + 9 次 LLM 调用（c=4；deepseek 级模型每次 0.5–2s）。**LLM 主导**直到 ~4 万条库，之后插件侧 O(N) 扫描反超。
- **睡眠周期**在生产中还要加真实 gist/QA LLM 调用（每簇 2 + 3×qaPairCount 次），但那是簇数 × 秒级的可控项；O(N²) 聚类本身才是规模项。
- deterministic 嵌入的**成本结构与真实嵌入相同**（同维度、同归一化、同扫描路径），只有余弦分布不同（已在睡眠基准中校准处理），故以上外推对生产有效。

### 优化建议（优先级排序，均有实测锚点）

1. **余弦热路径去掉重复范数计算**（`src/metrics.ts` `cosine`）：索引与记录的向量在写入时已归一化，但 `cosine()` 每次仍做 3 遍 1024 维循环（两个范数 + 一个点积），点积 1 遍即够。受益面 = L0 检索 + similar + refreshNeighborhood + 聚类**全部**热路径，预期 ≈2–3× 直提；改动一个函数，无 schema/介质变更。
2. **睡眠聚类预筛**：连边前先用便宜的候选生成器（如分桶 LSH / 按 r_m 或随机投影取每条 top-m 候选再精确余弦）把 O(N²) 降到 O(N·m)；或直接限制池窗口（如最近 conWindow 条）——语义上也更贴「相对近期记忆」的定义。1 万条库的 4 分钟 → 秒级。
3. **嵌入 int8 + base64 量化**（TODO 既有项）：磁盘 −41%、loadAll 解析量与堆占用近似减半、`storage.version` 升版即换库。建议在接入真实嵌入端点后第一批做。
4. **第 7 步增量刷新**：r_m/red 只对邻域可能变化的记录重算（本批新写入 ± 近邻），而非全库。睡眠周期无压缩时的 O(N²) 刷新随 2 一起消解。
5. **（可选）L0 换 ANN**：`VectorIndex` 接口已为替换留位。在上面的 1/2/3 落地后，10 万条以内的线性扫描配合点积快路径（~15ms/万条）大概率已够用，可推迟。

### 复现性与置信度

- 全部语料/查询由种子 PRNG 生成（同种子同语料）；每个 sqlite 场景独占新库文件，跑完即删（`tmp/`）。
- 每表数字为单次完整运行（非多轮取最优）；逐 op 采样给出 p95，规模曲线的 R² 均 ≥0.999，复杂度结论稳健；绝对值跨机不可比（本机 Ryzen 7 9700X），**比值与指数可跨机参考**。
- heap 测量受 GC 时机影响（两次独立测量 13.9/17.0 KB/条），按区间报告。
